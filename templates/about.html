How it works

Ask a question in plain English.
Get an answer grounded in real data.

This app doesn't guess - every answer is produced by translating your question into a real SPARQL query, running it against a live knowledge graph of Hungarian cultural heritage, and summarising only what came back. Here's exactly what happens between your message and the reply, and what data it's actually drawing from.

01

The pipeline

Every message runs through the same five stages, in order. Nothing is answered from general knowledge - if a stage can't ground the question in the graph, the pipeline says so instead of improvising.

1
Check the question against the schema Claude
Before writing a single line of SPARQL, the model checks whether the question even maps to something this graph tracks - using only the class and property names that actually exist in it. Questions about the weather, stock prices, or anything outside the schema are turned away here rather than answered with unrelated data.
2
Resolve named entities Claude Live lookup
Names in this graph are almost entirely Hungarian, so a question like "the Hungarian Central Statistical Office" won't match the stored string on its own. This step asks the model for candidate spellings and translations, checks each one against the graph for real, existing matches, and hands generation the exact stored string instead of a guess.
3
Generate a SPARQL query Claude Validated
The model writes one SELECT query, constrained to the curated schema below - no invented properties, no write operations, always scoped to the correct named graph. If the first attempt comes back empty, one broader retry is allowed before reporting nothing found.
4
Run it against the live endpoint SPARQL
The query executes against SZTAKI's public Fuseki/Virtuoso endpoint in real time. Results are capped at a safe row limit so a malformed or overly broad query can't overwhelm the app.
5
Visualize, then summarize Claude
If the results have a meaningful shape to plot - a breakdown by year, publisher, or content type - a chart is generated automatically. Finally, the model writes a short plain-English answer using only the rows that actually came back; it's told explicitly not to invent data or narrate a chart that wasn't made.
02

What data it uses

Everything comes from one named graph inside SZTAKI's public Linked Open Data endpoint - a catalogue of Hungarian cultural heritage works (largely digitised radio programming) and the people who created them.

03

Guardrails

A few things this pipeline deliberately does, so answers stay trustworthy rather than just fluent.

✓
Schema-only questions
If a question doesn't map to a real class or property in the graph, it's declined before any query is written.
✓
Read-only queries
Only SELECT statements are allowed - INSERT, DELETE, DROP and similar are rejected outright.
✓
Always graph-scoped
The endpoint hosts several unrelated datasets sharing the same property names - every query is forced inside the correct named graph so results never mix in unrelated data.
✓
No invented facts
The summary is written strictly from the rows that came back from the query - it's explicitly instructed not to fill in gaps.
